Knowledge Graphs & Property Graph Modeling

Why relational SQL joins explode on multi-hop network paths, and how property graphs model financial crime.

In Phase 1–4, we built an enterprise vector pipeline. But as our initial lesson revealed, vectors cannot answer: "Which shell companies share a nominee director with Sanctioned Trader X and wired funds to Account 9901?"

A natural reaction for a DevOps engineer is: "Why not just put entities in PostgreSQL or BigQuery and use relational foreign keys?" Let's examine why relational databases collapse under multi-hop relationship queries.

The "Join Explosion" Problem in SQL

In a relational database, relationships are not stored as physical connections; they are calculated dynamically at runtime by scanning primary/foreign key indexes across tables (JOIN accounts ON ... JOIN transfers ON ... JOIN companies ON ...).

  • 1 Hop (Direct join): Fast ($O(\log N)$ with B-tree index).
  • 2 Hops: Acceptable.
  • 5 Hops: Catastrophic join explosion. If each entity has 20 relationships, traversing 5 hops requires evaluating $20^5 = 3,200,000$ join operations! The query planner grinds disk I/O to a halt.

The Graph Alternative: Index-Free Adjacency

In a graph database like Neo4j, nodes physically store direct pointers in memory/disk to their neighboring nodes. Navigating an edge does not require scanning an index table—it simply dereferences a memory pointer in $O(1)$ time!

Whether the database contains 1,000 nodes or 10 billion nodes, traversing a 5-hop path takes microseconds because search time is proportional to the subgraph size, not the total table size.

The Property Graph Data Model for AML

The standard model in Neo4j is the Labeled Property Graph (LPG):

(:Person)
id: "P_101" name: "Dmitri V." nationality: "CY"
[:BENEFICIAL_OWNER_OF] share_pct: 100% • since: "2021-03" ↓
(:Company)
id: "C_402" name: "Apex Maritime Ltd" jurisdiction: "BVI"
[:HOLDS_ACCOUNT] status: "ACTIVE" ↓
(:Account)
iban: "CY29X10029" balance: $4,500,000 USD
[:TRANSFERRED] amount: $250,000 • date: "2024-08-14" ↓
(:Account • FROZEN)
iban: "GB88CHAS9901" is_frozen: true

Designing Nodes vs. Edges vs. Properties

When modeling financial crime data, follow these engineering guidelines:

  1. Nodes = Nouns / Entities: Physical or legal actors with identity (Person, Company, BankAccount, PhysicalAddress).
  2. Edges = Verbs / Actions: Directed connections (BENEFICIAL_OWNER_OF, TRANSFERRED, REGISTERED_AT).
  3. Properties = Attributes: Key-value data that describes an entity or an action (e.g., transaction amount, timestamp, birth date).
